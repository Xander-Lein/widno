# Orchestrate

## Чеклист

- [ ] 1. Проверить, действительно ли нужна декомпозиция; простую задачу оставить одному агенту.
- [ ] 2. Назначить дорогую модель координатором только там, где нужны архитектура,
  синтез результатов или решение с высокой ценой ошибки.
- [ ] 3. Разделить работу по границам модулей, а не по случайным файлам.
- [ ] 4. Для каждой подзадачи определить узкую роль субагента, входы, выходы,
  изменяемые файлы, зависимости и критерии проверки.
- [ ] 5. Выбрать режим: параллельные read-only исследования, независимые worktrees
  или последовательная передача ownership через handoff.
- [ ] 6. Ограничить инструменты и права субагента минимально необходимыми.
- [ ] 7. Выделить критический путь и задачи, которые можно выполнять параллельно.
- [ ] 8. Передать субагентам короткий контекст и ссылки на исходные документы,
  а не копировать большие логи в основной контекст.
- [ ] 9. Назначить отдельный validation step: координатор проверяет diff,
  тесты и критерии, а не принимает сообщение «готово» на веру.
- [ ] 10. Ограничить число параллельных субагентов и review-раундов.
- [ ] 11. Сохранить structured result: статус, изменения, проверки, ограничения
  и commit или read-only evidence.

## Шаблон задания субагенту

```text
Роль:
Цель:
Контекст и ссылки:
Разрешённые файлы:
Запрещённые действия:
Ожидаемый результат:
Критерии проверки:
Команда проверки:
Формат отчёта:
```

## Когда не делегировать

Не запускай субагентов, если задача короткая, последовательная или требует
изменения одного общего хрупкого участка. Не запускай параллельные задачи без
изоляции, если они могут редактировать одни и те же файлы.

Подробное обоснование правил: [agent workflows](../../../docs/agent-workflows.md).
