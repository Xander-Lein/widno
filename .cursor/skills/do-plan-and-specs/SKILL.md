# Спецификация и план

## Чеклист

- [ ] 1. Прочитать ответы пользователя, контекст репозитория и результаты классификации.
- [ ] 2. Зафиксировать цель, scope и явно перечислить, что не входит в задачу.
- [ ] 3. Описать контракты: входы, выходы, состояния, ошибки, совместимость и границы доступа.
- [ ] 4. Сформулировать проверяемые критерии приёмки для каждого пользовательского сценария.
- [ ] 5. Разбить работу на независимые вертикальные задачи и указать зависимости между ними.
- [ ] 6. Для каждой задачи указать изменяемые файлы, способ проверки и критерии готовности.
- [ ] 7. Описать риски, неизвестные, допущения и требующие решения вопросы.
- [ ] 8. Решить, нужна ли делегация: простую задачу оставить одному агенту.
- [ ] 9. Для сложной задачи назначить дорогую модель координатором, а субагентам
  передать независимые узкие задачи с ограниченными правами и фиксированными проверками.
- [ ] 10. Указать, какие задачи идут параллельно, какой нужен handoff и где требуется worktree.
- [ ] 11. Показать спецификацию и нумерованный план пользователю для утверждения.
- [ ] 12. После утверждения создать отдельную ветку или Git worktree до начала реализации.
- [ ] 13. Передать утверждённый план в `do-tdd-loop`.

## Формат результата

Используй разделы: `Контекст`, `Scope`, `Контракты`, `Критерии приёмки`, `Task graph`, `Риски`, `План проверок`, `Изоляция`.

Не пиши production-код до утверждения плана. Если создание ветки или worktree невозможно, остановись и сообщи причину.

Каждый субагент должен получить только необходимый контекст и вернуть структурированный
результат: статус, изменения, проверки, ограничения и commit либо read-only evidence.
Координатор обязан проверить результат самостоятельно.
